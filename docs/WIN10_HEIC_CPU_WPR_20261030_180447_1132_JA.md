# WicHeic 1.1.32 — Windows10実機CPU再測定（2026-10-30 18:04～18:08 JST）

## 結論と最優先目標

**CPU高負荷軽減が第一目的。** ユーザーは1.1.32最新版のMSIを使用。今回のユーザー提供CPU WPR ZIPのログから、対象 `dllhost.exe` のCPUピークは **46%**、WPR記録中の平均は **21.51%** であり、以前の1.1.31診断（ピーク87%、平均43.05%）より大幅に低い。

本バージョンの **gridタイル2＋HEVC 1ワーカー設定が実機でも選択されている**。ただし、個別画像の復号時間は増加しており、速度・CPU総仕事量・画像枚数が異なる2セッションを使った厳密なA/Bではない。**「CPU高負荷は今回大きく抑制されている」までは確認、完成・全面解決の断定はしない。**

## データの完全性・プライバシー

- 非公開の元資料：ユーザー提供 `COM_CPU_WPR_Manual_20261030_180447_054.zip`。**写真・ETL・WICログ原文・ユーザーのフルパスはGitHubに一切アップロードしない。**
- マニフェストは古い診断キット識別子「1.1.30」のまま。**実行中のWIC本体の製品版を示すものではない**。ユーザーは最新版1.1.32を使用と申告。下記の新実装固有イベント `DecoderTileBudget`, `DecoderGridWorkerBudget`, `DecoderWorkerSelect` でも新規タイル制御の動作を裏付ける。
- ZIP全8エントリー、全CRC検査成功。ETL本体1,902,116,864 bytesのSHA256は `DF20B90B65C979777DA96B093A59B387D03C4FA39EA34680BFD98ECC84BD6CBE` でmanifestと完全一致。WPR stop return 0、COMPLETE。

## 重要な留保

- **CPUの瞬間占有は確実に低下しているが、その一因は画像復号ペースが低くなったことかもしれない**。単純なCPU%/full-decodeを性能改善指標にしない。双方のセッションは撮影時刻、ファイル表示状態、WPR記録時間と処理数が異なる。
- CPU時間を直接測る `GetProcessTimes` の人工12MP WIC CIでは grid 4/codec4→grid2/codec1により **343.75→234.38ms（31.8%削減）**、壁時計は126.29→142.48ms（12.8%増）、画素完全一致（[#41026999004](https://github.com/taku077/wic_heic/actions/runs/41026999004)）。**この割合が実機にも当てはまるとは保証できない。**
- WindowsのPhotosプロセス（複数インスタンス）のCPU負荷、Explorerの負荷、表示遅延やフォト応答は別指標。今回の主対象dllhost以外のCPUピークもあり、**PC全体のCPUや体感改善を保証しない**。
- WICイベントの正常な `DecoderFullDecode` だけで失敗がないと推測しない。PhotosのEncoderSetThumbnail/MetadataWriterUnavailableなど一部未サポートAPI応答が存在するが、過去版との機能差の証拠にはならず、CPU解析と混同しない。
- 本番ユーザーの写真を上書きせず、個人ファイルパスをGitHubに記録しない。IMG_4074復元済み原本を再利用しない。**追加の大容量WPRを直ちに要求しない**。

## 次の現実的な判断

1. **1.1.32のCPU高負荷制御は適用成功**。ユーザーの実感するExplorerの使用感を最終判断で併用する。
2. 新たなMSIを頻繁に配布しない。既存の1.1.32が実機で実用的であれば、CPU低負荷と表示遅延の落としどころとして扱う。
3. もしサムネイルの表示が許容できないほど遅い場合は、タイル・HEVCの混合設定を **CPUピークの許容上限付き** で再比較する（CPU高負荷対策を後回しにしない）。実機の元画像を変更しない。

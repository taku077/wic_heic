# WicHeic 1.1.28 x64 — 2026-10-27 暫定改善版／実機未検証

## 位置付け

Windows 10 標準フォトでHEICをHEVC拡張購入なしに閲覧・編集・回転保存するための自作WICの**暫定MSI候補**。既存の1.1.27を置き換える上位バージョン（`Installer/Package.wxs` のWiX `Package Id` と `MajorUpgrade` は維持）。**Windows Server 2022 CIの合格はWindows 10フォト実機検証を意味しない**。

### 1.1.27からの主な差分（内部高速化・安全性）

- `CHeicBitmapDecoder::Initialize` で確定したHEIF画像IDごとに、小さなネイティブ `heif::ImageHandle` 共有参照を遅延保持。繰り返し `GetFrame(index)` での不要な画像ハンドル再取得を省く。**RGB全画素をデコーダーに永続キャッシュする変更ではない**。
- 同一COMデコーダーに対する初回の複数スレッドアクセスを `m_TopLevelHandleMutex` で同期。Photosの無再圧縮回転ソースを一度だけ公開するフラグをatomic化。
- 4ワーカー×32回 `GetFrame` の寸法・pixel format照合、4ワーカーの**別フレーム同時full RGB復号・全画素一致**、同一フレームの並列CopyPixels、2画像×300回列挙・RGB一致を人工HEICで検証する回帰試験。
- 大量の `GetFrame` 速度測定を `--getframe-latency` 独立モードに分離。WIC診断有効時の2MiB上限を埋め、保存経路イベントが消える以前のCI障害を解消。既存の診断制限、プライバシー条件、回転保存テストを緩めない。
- GitHub ActionsのpushイベントでもコミットSHAからジョブURL・成功/失敗を追跡できる `ci/wic-heic-x64` ステータスを追加（開始時pending、終了時final）。

### 既存機能

1.1.27でユーザー確認済みの警告抑制・編集/回転ボタン、IMG_3916を含む保存動作、ICC/Exif/HEIFコンテナ保持の可能な範囲、回転後の保存、Windows10フォトへのWIC登録を**変えない**。ただし、これらがすべての画像で完全に成立する保証はない。

### 改善効果と未解決点

**Windows 10実機での高速化％は未測定**。GitHub runnerでは1,000回のウォームGetFrameに約5.81msの記録があるが、診断ON時の約58.86msとは条件が違い、比較して「10倍速い」とは言えない。初回HEVC全画素復号の大幅高速化（目標10～20%、長期30%）は未達。標準フォトの6～7秒画像消失、縦横比崩れ、回転サムネイル反映遅延も未解決／未検証。

### MSI候補の公開条件

`.github/workflows/repair-x64-build.yml` の `release(candidate):` で始まるコミットからだけ、Windows Actions `compile-x64` の全工程（人工画像復号・回転・保存・再読み込み・50回ストレス、診断ログ制限、レジストリの隔離・復元、PowerShell5.1互換、MSIバージョン1.1.28、使い捨てrunnerでのMSIインストール／アンインストール）が成功したときに限り、MSIとSHA256を14日間アーティファクトとして公開する。**一般公開の完成版とみなさない**。

### 実機で試す場合の安全条件

- 1.1.27のインストーラー、重要画像の別コピー、現在のWIC登録状態を保全する。対象HEICは**複製だけ**を使い、初回はIMG_3916相当の二重回転メタデータ、ICC、縦長・横長、連続回転、回転保存後再オープンを確認する。
- MSIは1.1.28で1.1.27への上書き更新を狙うが、**Windows 10実機の1.1.27→1.1.28更新動作は未検証**。CIは使い捨てWindows Serverのクリーンな環境でのインストールと復元の確認。
- 警告再発、編集ボタン無効、フォト内の6～7秒消失悪化、画素・Exif異常があれば作業中止。1.1.27のMSIと登録状態の復元手順を用いて元の環境に戻す。元ファイルを直接上書きしない。

## 2026-10-27：1.1.28実機ユーザー報告：PNG共通表示崩れ／HEIC特有の重症化

ユーザーが **Windows 10実機にWicHeic 1.1.28を導入済み**。以下は目視による観察であり、定量計測ではない。

| 分類 | 実機からの報告 |
|---|---|
| 1.1.28の速度 | 体感の目視だけでは、1.1.27から改善したかどうか判別困難 |
| HEIC | 表示崩れが引き続き発生。過去からの「数秒間画像が消える」「画像表示領域が極端に狭くなる」「横長に引き延ばされる」問題は解消が確認されていない |
| PNG | 横長で固定される表示崩れが発生することが分かった。ただし回復は早い |
| PNGの重度症状 | HEICで見られた「画像が消える」「表示領域が極端に狭くなる」症状は、**現時点では再現していない**。発生しないとの断定はしない |

### 調査上の結論と優先順位

1. **横長に固定される共通症状**：PNGは自作HEIC専用WICデコーダーを通らない。Photosアプリの表示領域・画像配置・非同期再レイアウトなど共通の描画経路の問題を有力な仮説にする。ただし自作WICに固有の不具合を否定する材料ではない。
2. **HEICで顕著な画像消失／極端な領域縮小**：JPEG/PNGとの差を再現可能な条件で区別する。高いHEVC初回復号負荷（過去のCI同一人工画像でPNG/JPEGより大きい）は「描画更新の遅れを増幅する」仮説だが、**因果は未証明**。デコーダーからのWIC `GetSize`/pixel format/CopyPixels/Scaler/FlipRotatorの寸法一貫性と、PhotosのUI描画を別経路で検証する。
3. **次の実機診断の原則**：既存の画像やユーザー環境の破壊、WIC優先順位変更、標準コーデック無効化、繰り返しMSI更新を行わない。人工の**同じ可視画素・寸法・向き**を持つHEIC/PNG/JPEGで比較し、画像の表示状態を外部動画／スクリーンショットとWIC診断タイミングに分けて分析する。ただしフォト内部のレイアウト状態は自作WICログだけでは分からない。ユーザーに追加の負担を強いる前に既存テストとログを再利用する。
4. **1.1.28の評価**：CIで人工データの回帰合格は達成、実機導入も成立。ただし**表示崩れの解消と体感速度改善は未達／未認定**。1.1.28を正常表示完成版として扱わない。

## 2026-10-27：再現操作を確定 — ウィンドウフィットから追加縮小して回転

ユーザーによる1.1.28 Windows 10標準フォト実機の**同一操作・PNG/HEIC比較**：

1. **元画像の実寸より小さく**、フォトが最初からウィンドウに収まる大きさに自動調整した状態で画像を開く（初期ウィンドウフィットと解釈）。
2. この**既に縮小済みの表示を、操作でさらに縮小する**。
3. その状態から**画像を回転する**。
4. PNGでもHEICでも**横長で固定される表示崩れ**が再現する。PNGは比較的早く正常化、HEICでは遅延と画像消失・極端な表示領域の縮小という追加症状がこれまでに発生。ただしPNGの重症状は未再現というだけでゼロとは断定できない。

**優先仮説**：PNGを自作HEIC WICコードが復号しているわけではないため、共通の横長固定はフォトの縮小表示・回転・レイアウト反映の非同期状態遷移が関与している可能性が高い。HEICで増幅する追加症状はデコーダー遅延も候補だが、確定ではない。PNGとHEICで同じレンダリングエンジンかどうか、フォト内部実装は直接検証できない。画像のファイル内ピクセルが横長に変化したとする証拠はない。

### 追加した再現条件に近いWIC試験（フォト画面の再現ではない）

`wictest/WICFormatLatencyProbe.h` の既存`--perf-compare`（人工HEICから**同じ可視画素のPNG/JPEG**を生成する試験）を拡張し、同じ3形式で **元画像1080×1920 → 初期フィット540×960 → 追加縮小405×720 → 90度回転720×405** を行う。各段階の`GetSize`を検査し、回転直前のRGBと回転後のRGBを時計回り90度の座標写像で**全画素厳密一致**検査する。元フレーム寸法が変化しないことも確認する。新規MSIや診断インストール、ユーザー写真、既存ファイルの書き換えは不要。

- CIのこの検査が成功しても、**標準フォトのUI描画領域の更新まで正しいことは示せない**。WICで正常・フォトで異常なら、疑うべき層を狭める資料になる。
- 既存の`WICPhotosScaleMatrixProbe`はHEICの「スケール→回転」と「回転→スケール」6ケースの**保存結果**試験。今回追加したものは **3形式で初期フィット→追加ズーム→回転した表示用画素と幾何の比較**であり、既存の保存テストを作り直していない。
- 初期ズーム倍率、回転ボタンのUI操作種別、フォトのアプリ版数、レンダリング経路の内部詳細は現時点では未測定。数値540→405は**人工的な比較条件**であり、実機の倍率と断定しない。

外部照合：Microsoft Photosのウィンドウフィット自動拡大縮小の更新（2024年） https://blogs.windows.com/windows-insider/2024/10/22/microsoft-photos-update-with-super-resolution-begins-rolling-out-to-windows-insiders/ 。WIC `IWICBitmapScaler`と回転 `IWICBitmapFlipRotator` の動作 https://learn.microsoft.com/en-us/windows/desktop/api/wincodec/nn-wincodec-iwicbitmapscaler ; https://learn.microsoft.com/en-us/windows/desktop/api/wincodec/nn-wincodec-iwicbitmapfliprotator 。別ビューアのフィット時レイアウトの類似報告（同じ原因とは未証明） https://newsgroup.xnview.com/viewtopic.php?t=49510 。


## 2026-10-27：バッファー有無の回転走査A/B・新たな反証材料

Windows Actions [#40480933016](https://github.com/taku077/wic_heic/actions/runs/40480933016) **SUCCESS**。変更 `wictest/WICFormatLatencyProbe.h` は人工1080×1920画像で **初期フィット540×960 → 追加縮小405×720 → 90度回転720×405** とし、回転後405行を`IWICBitmapSource::CopyPixels`で1行ずつ読む処理を次の2方式で実測。3回の中央値、同じWindows Server 2022 runner内、内容はHEICの可視画素から作ったPNG/JPEGと比較。

| 形式 | A: lazy scaler→scaler→rotator・405回行読取 | B: 縮小後`IWICBitmapCacheOnLoad` → rotator・405回行読取 | B: 追加の事前バッファー構築 |
|---|---:|---:|---:|
| HEIC | **136.4064 ms** | **1.7871 ms** | 45.2246 ms |
| PNG | **3049.7421 ms** | **1.9095 ms** | 10.9899 ms |
| JPEG | **1013.3083 ms** | **1.8872 ms** | 3.7070 ms |

- いずれもA/B全画素**厳密一致**（`exact_rgb_equal=1`）かつ、先に作成した3形式の元画像サイズ・縮小・回転の全画素対応検査もPASS。
- Bの1.8～1.9msは**バッファーの構築45/11/4msを含まない**。1回目にBを使うコストを過少に比較してはいけない。出力は405行、バッファーの元画像は405×720×24bit = 874800バイト（約0.83MiB）。
- **注目：このWIC遅延パイプラインではPNGがHEICよりはるかに遅い。** 一方、ユーザーが報告した実機標準フォトでは、PNGの横長固定は速く回復し、HEICで画像消失／極端な領域縮小が顕著。**そのため、WICのこの合成パイプラインだけで実機症状の原因を説明することはできない**。Photosがどのフィルター・キャッシュ・描画APIを実際に使っているかは未確認。
- 根拠：Microsoft `IWICBitmapScaler` の`CopyPixels`時再サンプリング・バンド化最適化 https://learn.microsoft.com/en-us/windows/desktop/api/wincodec/nn-wincodec-iwicbitmapscaler ; `IWICBitmapFlipRotator` のバッファーなしピクセル／走査線アクセスに伴う計算量 https://learn.microsoft.com/en-us/windows/desktop/api/wincodec/nn-wincodec-iwicbitmapfliprotator 。
- 独立の2026年6月のWindows 10 Photosフォト編集画面の白画面・狭い表示領域事例 https://learn.microsoft.com/en-us/answers/questions/5912857/potential-display-bug-for-microsoft-photos-when-ed は存在。ただし回答者の「GPUハンドシェイクが原因」という推測には裏付けがなく、**今回との因果を断定しない**。別のImageGlass表示領域再計算の原因追跡例 https://github.com/d2phap/ImageGlass/issues/2387 も他アプリの実装であり同一原因を示さない。

### 次の開発判断

1. **現行実機WicHeic 1.1.28を維持**。本A/Bはテストコードのみの変更で、Photosへ任意のバッファー構築を強制できるわけではない。小さなベンチ成果でMSIを乱発しない。
2. ユーザー画像・元ファイルを変更しないこと、Windows標準コーデックの登録を触らないことを維持。WICコーデックの改善を行う場合は、実機フォトの画面更新とWICイベントの**相関を観測できる方法**（できればインストール不要・読取専用）を先に検討する。
3. 「横長固定」（PNG共通）と「画像消失／極端な表示領域縮小」（HEICで目立つ）は別トラックとし、後者についてHEIC `DecoderFullDecode`、`GetFrame`、`CopyPixels`のタイミングだけでは説明できない約6～7秒がどの段階で生じるか確認する。WICのPNG/HEIC独立したテストの速度値を、Photosアプリ内部の描画時間と混同しない。

## 2026-10-27：F9マーク2回の正確な操作時系列（ユーザー再訂正・旧解釈を撤回）

**最終確認されたユーザーの実機操作説明**：

1. 標準フォトを前面にしたまま、画像の縮小・回転で**最初の表示崩れが発生したため、F9を1回押した**。これは単なるキー動作確認ではなく、**実際の表示異常を示す第1マーク**である。F9を押す時点でフォトが前面にあった。
2. 診断ツールにF9が記録されたか確認するため、**その後**コマンドプロンプトを一時的に前面へ切り替えた。
3. コマンドプロンプトで記録を確認した後、標準フォトを再び前面に戻そうとしたところ、**表示崩れが一時的に正常へ復旧した**。いつ・何が描画を修正したかは観測していないため、ウィンドウ切り替えによる再描画が原因だとは確定しない。
4. フォトで縮小と回転を繰り返したところ、**再び表示崩れが発生**。フォトを前面にしたまま**F9をもう一度押した**。これは**第2の表示異常マーク**である。

### 対応する数値ログ（JST）

| 時刻 | 意味 |
|---|---|
| **21:27:26.14** | **第1の表示崩れ**が発生したためF9（フォト前面） |
| 21:27:29.98 | コマンドプロンプトを前面にし、F9の記録を確認（PIDが切り替わった） |
| 21:27:33.23 | フォトに戻す（PIDが元に戻った）。この切り替えの際に表示崩れが**一時的に復旧** |
| **21:27:44.94** | **再発した第2の表示崩れ**に対しF9（フォト前面） |

**旧記録の「1回目はキー動作確認だけで、表示異常ではなかった」という記述を明示的に撤回**。両マークとも異常発生を知らせるための押下であり、間に一時復旧と再操作がある。F9間隔18.796秒は**単一の表示異常の継続時間ではない**。F9は異常発生後に目視して押した手動時刻であるため、発生開始の正確なタイムスタンプでもない。

### 技術的な示唆と限界

- **フォトから別のウィンドウに切り替え、戻すと症状が一時的に解消した**という新しい実機観察は、フォト側のフォーカス変化・再描画・レイアウト再計算・キャッシュ更新等を調査する価値を高める。ただし、それらのどれが起きたかは直接記録していないため原因は未特定。
- 既存WICログに6～7秒の単独`DecoderFullDecode`はない。ただし復号器の周囲の処理、フォト描画状態、未記録の処理などを除外できない。
- 両マーク時点の前面ウィンドウ所有PIDが同じことはユーザー操作説明と整合する。WICイベント側のPID一致や時間的近接だけで、当該表示異常を引き起こした証拠とはならない。
- 診断の`WM_HOTKEY`は登録スレッドのメッセージキューへ通知される（https://learn.microsoft.com/ja-jp/windows/win32/inputdev/wm-hotkey）。キー記録とUI表示異常との関係には人手の認識・押下までの時間差がある。
- 本訂正は開発記録のみ。**実機の診断ZIPや個人のPID情報一覧はGitHubへアップロードしない**。WicHeic 1.1.28のMSIやWIC登録は変更しない。
